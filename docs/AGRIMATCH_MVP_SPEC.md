# AGRIMATCH MVP SPEC

เวอร์ชัน: 1.0  
วันที่: 18 พฤศจิกายน 2026  
ระยะพัฒนาเป้าหมาย: 6 วัน  
ภาษาใช้งานหลัก: ไทย  
ผู้ใช้หลัก: เกษตรกร / โรงงานอัด / โรงงานรับซื้อปลายทาง

## 1. เป้าหมายโครงการ

Agrimatch เป็นระบบช่วยนำเศษวัสดุทางการเกษตรเข้าสู่การใช้งาน โดยเชื่อมเกษตรกร โรงงานอัด และโรงงานรับซื้อ ผ่าน LINE และ Dashboard ใช้ Amazon Bedrock ช่วยสนทนา รวบรวมข้อมูล และอธิบายผล ส่วน Matching Engine ใช้กติกาที่ตรวจสอบได้ในการคัดกรองและจัดอันดับ

เป้าหมาย MVP คือให้ผู้ใช้ลงข้อมูล ค้นหาคู่ค้า ส่งข้อเสนอ และจบรายการเมื่อเกิดข้อตกลงรับซื้อในระบบได้จริง การรับซื้อในระบบหมายถึงการยืนยันข้อตกลง ไม่ใช่หลักฐานว่าชำระเงิน ส่งมอบ หรือตรวจคุณภาพแล้ว

## 3. ข้อตกลงออกแบบสำหรับเริ่มพัฒนา

รายการนี้เป็นค่าเริ่มต้นที่กำหนดในสเปก ไม่ใช่การอ้างว่าผู้ใช้เลือกทุกรายละเอียดแล้วหรือมีระบบเหล่านี้อยู่ในโค้ดเดิม

- ใช้ TypeScript ทั้งเว็บและ Backend; Matching อยู่ใน Backend เดียวกัน
- ใช้ Vercel สำหรับเว็บ และ Railway สำหรับ API, worker และ PostgreSQL ตามแนวทางเดิม; Bedrock อยู่บน AWS
- ใช้ S3 เก็บภาพประกาศแบบ private; Leaflet เป็นส่วนเสริมเมื่อมีเวลาสำหรับแผนที่
- ยังไม่ยืนยันว่ามีโค้ด ฐานข้อมูล LINE OA หรือบัญชีบริการพร้อมใช้งาน ต้องสำรวจในวันแรก
- หนึ่งรายการขายผูกกับวัสดุหนึ่งชนิดและหนึ่งตำแหน่ง หากต่างชนิดหรือต่างสถานที่ให้แยกรายการ
- การตกลงซื้ออาจครอบคลุมบางส่วนของปริมาณได้ ต้องหักหรือจองปริมาณอย่างถูกต้อง
- ใช้รายการวัสดุเริ่มต้น เช่น ฟางข้าว ใบอ้อย ซังข้าวโพด และรายการ “อื่น ๆ” ที่ต้องยืนยันประเภทก่อนจับคู่อัตโนมัติ
- ไม่เพิ่มระบบคาร์บอนเครดิตหรือค่าลดการปล่อยที่ไม่มีวิธีคำนวณและข้อมูลยืนยันใน MVP

## 5. ช่องทางและหน้าจอ

### 5.1 LINE เกษตรกร

เมนูหลัก: คุยกับผู้ช่วย / ลงขายวัสดุ / หาผู้รับอัด / รายการของฉัน / ข้อเสนอ

- ส่งข้อความ รูปภาพ และตำแหน่งได้
- AI เริ่มจากถามว่าอยากขายวัสดุ หาผู้รับอัด ดูข้อเสนอ หรือสอบถามเรื่องใด
- ถามข้อมูลที่ขาดทีละเรื่อง ไม่บังคับกรอกแบบฟอร์มยาว
- แสดงสรุปก่อนเผยแพร่พร้อมปุ่ม “ยืนยันเผยแพร่”, “แก้ไข”, “เก็บร่าง”
- แสดงข้อเสนอพร้อมปริมาณ ราคา หน่วยราคา ผู้รับผิดชอบขนส่ง และปุ่มตอบรับ/ปฏิเสธ

### 5.2 LINE โรงงานอัด

เมนูหลัก: คุยกับผู้ช่วย / ตั้งรับอัด / ตั้งรับซื้อ / ข้อเสนอ / ขายต่อ / เปิด Dashboard

ต้องแยกให้เห็นว่า “รับจ้างอัด” คือบริการที่เกษตรกรยังเป็นเจ้าของวัสดุ ส่วน “รับซื้อเพื่อขายต่อ” คือธุรกรรมซื้อขาย AI ถามให้ชัดก่อนสร้างร่างหากข้อความกำกวม

### 5.3 LINE โรงงานรับซื้อ

เมนูหลัก: คุยกับผู้ช่วย / ตั้งความต้องการ / ผลจับคู่ / ข้อเสนอ / เปิด Dashboard

ใช้ LINE ตั้งความต้องการ ดูคู่ค้าที่เหมาะสม และตอบรับข้อเสนอได้โดยไม่จำเป็นต้องเปิดเว็บทุกครั้ง Dashboard เป็นช่องทางเสริมสำหรับดูและจัดการหลายรายการ

### 5.4 Dashboard โรงงานทั้งสองประเภท

- ภาพรวม: ประกาศที่เปิดอยู่ ผลจับคู่ ข้อเสนอรอตอบ และข้อตกลงรับซื้อ
- ความต้องการรับซื้อ: สร้าง แก้ไข เปิด/ปิด พร้อมเงื่อนไขวัสดุและการขนส่ง
- ผลจับคู่: รายการวัสดุ เหตุผล คะแนนแยกองค์ประกอบ และข้อมูลที่ยังขาด
- ข้อเสนอและข้อตกลง: ดูรายละเอียด ส่งข้อเสนอ ตอบรับ และดูประวัติ
- ผู้ช่วย AI: ช่วยกรอก/แก้ร่างและตอบคำถาม โดยใช้สิทธิ์และข้อมูลเดียวกับ LINE
- โรงงานอัดมีเพิ่ม: ประกาศรับจ้างอัด รายการซื้อเข้า และประกาศขายต่อ
- ตั้งค่าองค์กร: สถานที่ ผู้ติดต่อ สมาชิก และสถานะผูก LINE

หน้าเว็บเน้นใช้งานได้บนมือถือด้วย ไม่มี Dashboard เกษตรกรหรือหน้าแอดมินเต็มรูปแบบในขอบเขต 6 วัน

## 6. กระบวนการหลัก

### 6.1 เกษตรกรขายตรงให้โรงงาน

1. เกษตรกรบอก AI เช่น “มีฟางข้าว 5 ตัน อยู่กำแพงเพชร ไม่มีรถขน”
2. AI แยกข้อมูล ถามตำแหน่ง ราคา/เงื่อนไข และวันที่พร้อมขายที่ยังขาด
3. รับภาพและประเมินภายนอกเบื้องต้นเมื่อมีภาพ
4. แสดงร่างให้เกษตรกรตรวจสอบและกดยืนยัน
5. Matching Engine หาความต้องการซื้อที่ตรงเงื่อนไข
6. คู่ค้าส่งข้อเสนอพร้อมเงื่อนไข อีกฝ่ายตอบรับหรือปฏิเสธ
7. เมื่อทั้งสองฝ่ายยืนยันเงื่อนไขเดียวกัน บันทึกข้อตกลงรับซื้อ หักปริมาณที่ขาย และแจ้งทั้งคู่
8. รายการนี้จบตามขอบเขต MVP โดยไม่รอชำระเงินหรือขนส่ง

### 6.2 เกษตรกรจ้างโรงงานอัด

1. โรงงานอัดเผยแพร่บริการรับอัด พร้อมวัสดุที่รองรับ พื้นที่ ราคา/หน่วย ปริมาณขั้นต่ำ และรูปแบบบริการ
2. เกษตรกรแจ้งชนิดวัสดุ ปริมาณ สถานที่ วันที่ และต้องการเครื่องอัดไปหน้างานหรือส่งวัสดุไปอัด
3. ระบบจับคู่บริการที่ตรงเงื่อนไข
4. ส่งข้อเสนอบริการและยืนยันการจ้างได้
5. บันทึกเป็นข้อตกลงบริการ แยกจากข้อตกลงรับซื้อ ไม่เปลี่ยนเจ้าของวัสดุ ไม่สร้างสต็อกให้โรงงานอัด

บริการอัดไม่ใช่เงื่อนไขบังคับก่อนขาย เกษตรกรยังขายตรงได้ การติดตามงานอัดจนเสร็จไม่อยู่ใน MVP

### 6.3 โรงงานอัดซื้อแล้วขายต่อ

1. โรงงานอัดตั้งรับซื้อวัสดุและรับผลจับคู่จากเกษตรกร
2. เมื่อมีข้อตกลงรับซื้อ บันทึกรายการซื้อเข้านี้ให้จบได้โดยอิสระจากการขายต่อ
3. แสดงปุ่ม “สร้างประกาศขายต่อ” ทันที การกดปุ่มสร้างเพียงร่าง
4. AI นำข้อมูลที่เกี่ยวข้องมาเติม เช่น ประเภทวัสดุ ปริมาณที่ตกลงซื้อ และรหัสรายการต้นทาง
5. ถามข้อมูลใหม่: ปริมาณขายต่อ สภาพหลังอัด รูปแบบก้อน ราคาขาย สถานที่ และวันที่พร้อมส่ง
6. โรงงานอัดตรวจสอบแล้วกดยืนยันเผยแพร่
7. จับคู่ประกาศขายต่อนี้กับความต้องการของโรงงานปลายทาง
8. เมื่อโรงงานปลายทางตกลงรับซื้อ เกิดข้อตกลงใหม่ที่เชื่อมกับรายการต้นทาง

กติกาการขายต่อ:

- สร้างและเผยแพร่ได้หลังตกลงซื้อ โดยต้องแสดง “รอรับ/รออัด” และวันที่คาดว่าจะพร้อม หากยังไม่มีวัสดุพร้อมจริง
- ห้ามนำสถานะตกลงซื้อไปแสดงเป็นรับของแล้วหรืออัดเสร็จแล้วโดยอัตโนมัติ
- รูปภาพและผลประเมินของวัสดุก่อนอัดห้ามแสดงเป็นหลักฐานคุณภาพหลังอัด ต้องระบุแหล่งที่มาและช่วงเวลา
- เก็บสถานที่ต้นทางแยกจากสถานที่ขายต่อ ไม่คัดลอกข้อมูลติดต่อส่วนตัวของเกษตรกรมาเผยแพร่
- ปริมาณที่จัดสรรให้ร่าง/ประกาศขายต่อรวมกันต้องไม่เกินปริมาณซื้อเข้าที่ใช้ได้; แก้ปริมาณต้องตรวจสอบใหม่
- แสดงสถานะวัสดุคาดว่าจะพร้อมอย่างชัดเจนในข้อเสนอและให้ผู้ซื้อยอมรับเงื่อนไขนั้น
- ถ้ารายการต้นทางถูกยกเลิก ให้หยุดประกาศขายต่อที่พึ่งพารายการนั้นและแจ้งผู้เกี่ยวข้อง ข้อตกลงปลายทางที่ยืนยันแล้วให้ขึ้นสถานะต้องทบทวน ห้ามลบทิ้งเงียบ ๆ

### 6.4 โรงงานตั้งความต้องการด้วย AI

1. โรงงานบอกวัสดุ ปริมาณ เงื่อนไขคุณภาพ งบ และพื้นที่ที่รับได้
2. AI ถามข้อมูลที่ขาดและสร้างร่าง
3. โรงงานตรวจสอบแล้วเผยแพร่ผ่าน LINE หรือ Dashboard
4. เมื่อมีรายการใหม่หรือเงื่อนไขเปลี่ยน ระบบคำนวณคู่ที่ตรงเงื่อนไขใหม่

## 7. ข้อมูลที่ต้องเก็บ

### 7.1 ประกาศขายวัสดุ

- เจ้าของรายการ ประเภทวัสดุ และคำอธิบาย
- ปริมาณและหน่วย; เก็บน้ำหนักมาตรฐานเป็นกิโลกรัม โดย 1 ตัน = 1,000 กิโลกรัม
- ราคาที่ต้องการพร้อมหน่วย หรือ “ต่อรองได้” ซึ่งไม่เท่ากับราคา 0
- จังหวัด/อำเภอและพิกัดที่ผู้ใช้ส่ง; ห้ามสร้างพิกัดแน่นอนขึ้นเองจากชื่อจังหวัด
- วันที่พร้อมขาย สถานะวัสดุ และเงื่อนไขขนส่ง
- รูปภาพและผลประเมินเสริม แยกจากข้อมูลที่เจ้าของยืนยัน
- ปริมาณทั้งหมด ปริมาณที่ตกลงขาย และปริมาณคงเหลือ

### 7.2 ความต้องการรับซื้อ

- องค์กร ประเภทวัสดุและรูปแบบที่รับ เช่น วัสดุหลวมหรืออัดก้อน
- ปริมาณเป้าหมาย ปริมาณขั้นต่ำต่อครั้ง และปริมาณที่ยังต้องการ
- ราคาสูงสุดและหน่วย หรือระบุขอเจรจา
- สถานที่รับ รัศมีค้นหาหรือพื้นที่ที่ยอมรับ และช่วงวันที่ต้องการ
- เงื่อนไขคุณภาพที่ต้องการ พร้อมระบุว่าข้อมูลใดต้องตรวจยืนยัน
- ผู้จัดการขนส่ง และรับสินค้าที่กำลังรออัด/รอพร้อมได้หรือไม่

### 7.3 บริการอัดและคำขอรับบริการ

ชนิดวัสดุ รูปแบบการอัด พื้นที่ให้บริการ สถานที่ ปริมาณขั้นต่ำ ราคา/หน่วย ผู้รับผิดชอบขนส่ง ช่วงเวลาว่าง และให้บริการหน้างานหรือที่โรงงาน

### 7.4 ข้อเสนอ

ต้องมีคู่ค้า รายการอ้างอิง ประเภทธุรกรรม ปริมาณ ราคาและหน่วย ยอดรวมเมื่อคำนวณได้ เงื่อนไขขนส่ง วันที่พร้อม และวันหมดอายุข้อเสนอ ราคาขนส่งที่ยังไม่ทราบต้องแสดงแยก ห้ามรวมเป็นต้นทุนสุดท้ายที่ยืนยันแล้ว

## 8. ขอบเขต AI และ Amazon Bedrock

### 8.1 งานที่ AI ต้องทำได้

- เข้าใจเจตนา: ขายวัสดุ หาผู้รับอัด รับซื้อ รับจ้างอัด ขายต่อ ดูสถานะ หรือสอบถาม
- สนทนาต่อเนื่องด้วยบริบทของบทบาทและร่างที่กำลังทำอยู่
- ถามข้อมูลที่ขาด แปลงภาษาพูดและหน่วยให้เป็นข้อมูลโครงสร้าง
- ช่วยร่างและแก้ข้อมูลประกาศ ความต้องการซื้อ บริการอัด และประกาศขายต่อ
- อธิบายผลจับคู่จากข้อมูลและคะแนนที่ Backend ส่งให้
- ตอบคำถามการใช้งาน การเตรียมข้อมูลวัสดุ และสถานะรายการที่มีสิทธิ์เข้าถึง
- เมื่อไม่มีข้อมูลราคาตลาดหรือข้อเท็จจริงเฉพาะ ให้บอกว่าไม่ทราบและถามเพิ่ม ไม่แต่งราคา ผู้ซื้อ หรือสถานะงาน

### 8.2 รูปแบบการประมวลผล

Backend รับข้อความ → โหลดข้อมูลที่ผู้ใช้มีสิทธิ์ → ส่งบริบทให้ Bedrock → รับคำตอบและข้อมูลร่าง → ตรวจ schema/หน่วย/สิทธิ์ → บันทึกร่าง → แสดงตัวอย่าง → ผู้ใช้ยืนยัน → Backend ดำเนินการ

เลือกใช้ Bedrock Runtime Converse API เป็นแนวทางสำหรับ MVP โดยกำหนดขีดจำกัด token, timeout และ retry อย่างชัดเจน รูปแบบข้อความและข้อมูลภาพต้องตรงกับโมเดลที่เลือก ตาม [เอกสาร Converse ของ AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html)

- กำหนดโมเดลข้อความและโมเดลที่รองรับภาพผ่าน configuration ไม่ฝัง model ID ใน business logic
- ตรวจสอบสิทธิ์ โมเดล Region และข้อจำกัดจริงในวันแรกก่อนเลือก ID; เอกสารนี้ไม่ยืนยันความพร้อมของบัญชี AWS
- เก็บประวัติสนทนาแบบจำกัด พร้อมสรุปบริบทเพื่อควบคุมค่าใช้จ่าย
- ตรวจผลลัพธ์ด้วย schema เช่น Zod; ตัวเลข/วันที่ที่กำกวมต้องถามใหม่
- ไม่ต้องมี multi-agent, AgentCore, custom training หรือ Knowledge Base ใน MVP ใช้คำแนะนำที่ทีมตรวจแล้วและข้อมูลระบบก่อน
- ถ้า AI ใช้งานไม่ได้ ผู้ใช้ยังกรอกผ่านคำถามตามขั้นตอน/ปุ่ม หรือแบบฟอร์ม Dashboard และดูผลจับคู่ได้

### 8.3 ขอบเขตการดำเนินการ

AI สร้างหรือแก้ร่างได้ แต่ห้ามเผยแพร่ประกาศ ส่งข้อเสนอ ยืนยันซื้อขาย ยืนยันบริการ หรือยกเลิกข้อตกลงแทนผู้ใช้โดยไม่มีการยืนยันการกระทำนั้น

ข้อความ รูป และคำอธิบายที่ส่งเข้าระบบเป็นข้อมูล ไม่ใช่คำสั่งให้เปลี่ยนสิทธิ์หรือข้ามขั้นตอน Backend เป็นผู้ตรวจและตัดสินการเปลี่ยนสถานะเสมอ

## 9. การประเมินภาพเบื้องต้น

ฟีเจอร์นี้ต้องมีเส้นทางใช้งานใน MVP แต่เป็นข้อมูลเสริม การประเมินล้มเหลวหรือไม่มีรูปต้องไม่ขวางการลงขาย

- วิเคราะห์ประเภทวัสดุที่น่าจะเป็น สี สภาพภายนอก และสิ่งเจือปนที่มองเห็น
- ผลลัพธ์มีข้อสังเกต ข้อจำกัด ข้อมูลที่ยังต้องถาม และสถานะ “ประเมินไม่ได้” หากภาพไม่เหมาะสม
- แสดงข้อความ “การประเมินเบื้องต้นจากภาพ ไม่ใช่ผลตรวจคุณภาพจริง” ทุกจุดที่แสดงผล
- ไม่สรุปความชื้นเป็นเปอร์เซ็นต์ ค่าความร้อน หรือการผ่านมาตรฐานโรงงานจากภาพอย่างเดียว
- MVP ใช้ข้อสังเกตเป็นหลัก ยังไม่กำหนดเกรด A/B/C แบบรับรอง หากต้องการเกรดในอนาคตต้องมีเกณฑ์และข้อมูลทดสอบ
- ห้ามใช้ผลภาพเพียงอย่างเดียวตัดสิทธิ์การขายหรือถือว่าผ่านข้อกำหนดคุณภาพที่ต้องตรวจจริง
- เก็บผลประเมินผูกกับภาพ เวลาประเมิน และ model ID; เปลี่ยนรูปหรือแปรรูปวัสดุต้องไม่ใช้ผลเดิมเป็นผลใหม่

## 10. Matching Engine

### 10.1 ประเภทการจับคู่

1. ประกาศเกษตรกร ↔ ความต้องการโรงงานปลายทาง
2. ประกาศเกษตรกร ↔ ความต้องการซื้อของโรงงานอัด
3. คำขออัดของเกษตรกร ↔ บริการอัดของโรงงานอัด
4. ประกาศขายต่อโรงงานอัด ↔ ความต้องการโรงงานปลายทาง

### 10.2 กติกาคัดกรอง

- รายการต้องเผยแพร่ เปิดใช้งาน และมีปริมาณคงเหลือ
- ประเภทวัสดุ รูปแบบวัสดุ และประเภทธุรกรรมต้องสอดคล้องกัน
- ตรวจขั้นต่ำ ปริมาณคงเหลือ ช่วงเวลา เงื่อนไขพื้นที่ และความเป็นไปได้ของการขนส่ง
- ไม่จับคู่รายการกับองค์กรเจ้าของเอง
- หากเงื่อนไขบังคับไม่มีข้อมูลยืนยัน ให้แสดง “ต้องสอบถาม/ตรวจเพิ่ม” ไม่แสดงว่าผ่านแล้ว
- ระยะทางจากพิกัดใช้ Haversine และระบุว่าเป็นระยะทางเส้นตรง ไม่ใช่ระยะขับรถ
- หากไม่มีพิกัดให้จับคู่จากพื้นที่ที่ผู้ใช้ระบุได้ แต่ไม่อ้างว่าผ่านรัศมีแน่นอน

### 10.3 คะแนนเริ่มต้นที่ปรับค่าได้

สูตรสำหรับซื้อขาย: ระยะทาง 30% + ปริมาณ 25% + ราคา 20% + ช่วงเวลา 15% + ความสอดคล้องเงื่อนไข 10%

สูตรสำหรับบริการอัด: พื้นที่บริการ 35% + วัสดุ/รูปแบบการอัด 25% + เวลา 20% + ปริมาณ 10% + ราคา 10%

กำหนดแต่ละองค์ประกอบให้อยู่ช่วง 0–1 และคำนวณคะแนน 0–100 หลังผ่านกติกาคัดกรองแล้ว หากองค์ประกอบใดไม่มีข้อมูล ให้คำนวณเฉพาะส่วนที่ทราบโดยปรับน้ำหนักใหม่ พร้อมแสดงสัดส่วนข้อมูลที่ใช้ คะแนนที่ข้อมูลไม่ครบต้องมีป้าย “ข้อมูลไม่ครบ” และจัดหลังคู่ที่ยืนยันเงื่อนไขสำคัญครบในกลุ่มเดียวกัน

น้ำหนักเหล่านี้เป็นสมมติฐานเริ่มต้นสำหรับทดสอบเดโม ไม่ใช่สูตรที่พิสูจน์ว่าดีที่สุด เก็บคะแนนรายองค์ประกอบและ version กติกาไว้ตรวจสอบ AI อธิบายได้แต่เปลี่ยนคะแนนหรือสร้างคู่ค้านอกผลค้นหาไม่ได้

## 11. สถาปัตยกรรม

```text
LINE OA เกษตรกร ─────────┐
LINE OA โรงงานอัด ────────┼── HTTPS Webhooks ──┐
LINE OA โรงงานรับซื้อ ────┘                    │
                                               ▼
Dashboard Next.js ── HTTPS API ── Node.js / Express / TypeScript
                                  ├── Identity & Permissions
                                  ├── Conversations & Drafts
                                  ├── Listings / Demands / Services
                                  ├── Matching Engine
                                  ├── Offers / Agreements / Resale
                                  ├── Bedrock Adapter
                                  └── Notification / Job Worker
                                               │
                                  PostgreSQL + Private S3 Images
```

Backend เป็นแอปเดียวที่แบ่งโมดูลชัดเจน Worker ใช้ฐานโค้ดเดียวกันและตารางงาน PostgreSQL เพื่อประมวลผล AI/แจ้งเตือนแบบทนต่อการรีสตาร์ต ยังไม่เพิ่ม Redis, microservices, Python Matching Service หรือ PostGIS ใน MVP

### 11.1 การเชื่อม LINE สามช่องทาง

- แยก endpoint `/webhooks/line/farmer`, `/webhooks/line/baler`, `/webhooks/line/factory`
- แยก channel secret และ access token แต่ละบัญชี ตรวจลายเซ็นกับ raw body ก่อน parse ตาม [เอกสาร LINE](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/)
- ระบุบทบาทเริ่มต้นจาก channel ที่ผ่านการตรวจสอบ และตรวจสมาชิกองค์กรก่อนเข้าถึงข้อมูลโรงงาน
- เก็บ channel ID และ provider ID กับตัวตน LINE; ไม่รวมผู้ใช้จากชื่อแสดงผลเดียวกัน ตัว user ID ขึ้นกับ provider ตาม [เอกสาร user ID ของ LINE](https://developers.line.biz/en/docs/messaging-api/getting-user-ids/)
- วาง channels ของบริการเดียวกันภายใต้ provider ที่เหมาะสม และผูกข้ามช่องทางเฉพาะเมื่อมีสิทธิ์และความยินยอม
- กัน webhook ซ้ำด้วย channel ID + webhook event ID; รับงานลงฐานข้อมูลก่อนตอบรับ และทำ AI ต่อใน worker
- ส่งข้อความผ่านบัญชีที่ถูกต้อง ตรวจข้อจำกัดการส่งของ LINE และเก็บสถานะส่งสำเร็จ/ล้มเหลว
- หากแจ้งเตือนล้มเหลว ข้อตกลงยังอยู่ในฐานข้อมูลและเปิดดูจากเมนู/Dashboard ได้ ไม่ย้อนสถานะซื้อขายตามผลส่งข้อความ

### 11.2 การเข้าสู่ Dashboard

ค่าเริ่มต้น MVP ใช้บัญชีองค์กรที่ได้รับเชิญ พร้อมอีเมล/รหัสผ่านที่เก็บเป็น hash และ session/JWT ใน cookie แบบ HttpOnly, Secure พร้อมการป้องกัน CSRF ตามรูปแบบที่ใช้จริง

ผูก LINE กับสมาชิกองค์กรด้วยรหัสใช้ครั้งเดียวที่มีอายุสั้น ออกให้จาก Dashboard แล้วนำไปส่งใน OA ของบทบาทนั้น Backend ตรวจรหัสและองค์กรก่อนผูก ห้ามถือว่าการรู้ชื่อองค์กรหรืออีเมลทำให้เป็นสมาชิกได้

## 12. แบบจำลองข้อมูลขั้นต่ำ

| Entity | หน้าที่และข้อมูลสำคัญ |
| --- | --- |
| users | ตัวตนผู้ใช้ ข้อมูลติดต่อและความยินยอม |
| organizations | โรงงานอัด/โรงงานรับซื้อ ที่อยู่และข้อมูลกิจการ |
| memberships | ผู้ใช้ องค์กร บทบาทและสิทธิ์ |
| line_identities | ผู้ใช้ provider/channel/user ID บทบาท และสถานะผูก |
| conversations / messages | ประวัติสนทนาตามบริบทและร่างที่เกี่ยวข้อง |
| drafts | ประเภทร่าง เจ้าของ ข้อมูล version และสถานะตรวจสอบ |
| material_listings | วัสดุขาย ปริมาณคงเหลือ สถานที่ ราคา วันพร้อม และสถานะวัสดุ |
| purchase_demands | ความต้องการรับซื้อและปริมาณที่ยังต้องการ |
| baling_services | ประกาศรับอัดและเงื่อนไขบริการ |
| baling_requests | คำขออัดจากเกษตรกร |
| media / image_assessments | ภาพเจ้าของรายการและผลประเมินเบื้องต้น |
| matches | คู่ที่คำนวณ คะแนน องค์ประกอบ ข้อมูลที่ขาด และ rule version |
| offers | ผู้ส่ง/ผู้รับ ประเภทธุรกรรม เงื่อนไข version และสถานะ |
| agreements | ข้อตกลงที่ยืนยันแล้ว แยก purchase กับ baling_service |
| resale_allocations | agreement ต้นทาง ประกาศขายต่อ ปริมาณที่จัดสรร และสถานะ |
| webhook_events / jobs | กันประมวลผลซ้ำและงานเบื้องหลังที่ retry ได้ |

| audit_logs | ผู้กระทำ การกระทำ entity version และเวลา |

เก็บน้ำหนักและราคาเป็นชนิด decimal ที่กำหนด precision ชัดเจน ไม่ใช้ floating point สำหรับยอดเงิน บันทึกเวลาเป็น UTC และแสดงผล Asia/Bangkok

ข้อมูลขายต่อควรสืบย้อนกลับได้ แต่ห้ามคัดลอกหรือเปิดข้อมูลส่วนบุคคลต้นทางเกินสิทธิ์ของคู่ค้าปลายทาง

## 13. สถานะและความถูกต้องของธุรกรรม

### 13.1 ร่างและประกาศ

`DRAFT → AWAITING_REVIEW → PUBLISHED → CLOSED`

ประกาศอาจ `PAUSED` หรือ `CANCELLED` ได้ เมื่อแก้ข้อมูลสำคัญที่ AI สร้าง ต้องตรวจสอบ version ใหม่ก่อนเผยแพร่ การกดยืนยันจากข้อความเก่าต้องไม่เผยแพร่ร่าง version ใหม่โดยไม่ตรวจ

### 13.2 ข้อเสนอและการรับซื้อ

`PENDING → ACCEPTED | REJECTED | WITHDRAWN | EXPIRED`

- ผู้ส่งยืนยันเงื่อนไขเมื่อส่งข้อเสนอ ผู้รับยืนยันเมื่อกดรับ หากผู้ส่งเป็นผู้ขายและโรงงานกดรับ ข้อตกลงจบทันทีเมื่อผ่านการตรวจข้อมูล
- หากโรงงานเป็นผู้ส่งข้อเสนอ ต้องให้เจ้าของวัสดุกดรับด้วยก่อนถือว่าตกลงรับซื้อ
- การกด “สนใจ” หรือผลจับคู่ไม่ใช่การรับซื้อ
- เมื่อรับข้อเสนอ ให้ตรวจ version รายการ วันหมดอายุ ปริมาณที่เหลือ และสิทธิ์อีกครั้ง
- สร้าง agreement, หักปริมาณวัสดุ/ความต้องการซื้อ และเพิ่ม outbox ใน transaction เดียวกัน พร้อม lock ที่จำเป็น
- ข้อเสนอที่ยังรอตอบไม่หักสต็อก เมื่อสองคนกดรับพร้อมกันต้องไม่มีการขายเกินปริมาณ
- การกดซ้ำต้องคืนผลเดิม ไม่สร้าง agreement ซ้ำ
- การแก้เงื่อนไขข้อเสนอให้ถอนข้อเสนอเก่าและสร้างใหม่ ห้ามแก้เงื่อนไขที่รับแล้วเงียบ ๆ
- agreement รับซื้อใช้สถานะ `PURCHASE_CONFIRMED` ซึ่งเป็นจุดสิ้นสุด MVP ของรายการนั้น ไม่ตั้งชื่อว่า delivered หรือ paid
- บริการอัดใช้ `SERVICE_CONFIRMED` และไม่เข้ากระบวนการหักสต็อกซื้อขาย

## 14. กลุ่ม API ที่ต้องมี

ชื่อ endpoint เป็นแนวทางสำหรับพัฒนา ปรับให้เข้ากับโค้ดเดิมได้โดยคงพฤติกรรมและสิทธิ์

| กลุ่ม | ตัวอย่าง endpoint | ข้อกำหนด |
| --- | --- | --- |
| Auth | `/auth/login`, `/auth/logout`, `/me`, `/line-link-codes` | session และองค์กร |
| LINE | `/webhooks/line/:role` | raw body signature และ deduplication |
| Assistant | `/assistant/messages` | ใช้ role/context จาก session ห้ามเชื่อจาก client อย่างเดียว |
| Drafts | `/drafts`, `/drafts/:id`, `/drafts/:id/publish` | owner, version และยืนยันก่อนเผยแพร่ |
| Listings | `/listings` | ปริมาณและสิทธิ์เจ้าของ |
| Demands | `/purchase-demands` | โรงงานอัดหรือโรงงานรับซื้อ |
| Baling | `/baling-services`, `/baling-requests` | แยกบริการกับรับซื้อ |
| Matching | `/matches` | ผลตามสิทธิ์และข้อมูลที่เผยแพร่ |
| Offers | `/offers`, `/offers/:id/accept`, `/offers/:id/reject` | ตรวจ state และ transaction |
| Agreements | `/agreements`, `/agreements/:id/resale-draft` | ขายต่อได้เฉพาะโรงงานอัดที่เป็นผู้ซื้อ |
| Images | `/media`, `/media/:id/assessment` | ตรวจเจ้าของและชนิดไฟล์ |

ทุกช่องทางต้องเรียก business service ชุดเดียวกันเพื่อให้ LINE และ Dashboard เห็นสถานะตรงกัน

## 15. ขอบเขต 6 วัน

### ต้องส่งมอบ

- LINE OA 3 บัญชีและบทสนทนาตามบทบาท
- AI ช่วยเหลือ ถามข้อมูล สร้าง/แก้ร่าง และให้ผู้ใช้ตรวจสอบก่อนดำเนินการ
- เกษตรกรลงขายและขอรับบริการอัดผ่าน LINE
- โรงงานรับซื้อและโรงงานอัดตั้งความต้องการซื้อได้
- โรงงานอัดตั้งรับจ้างอัดและสร้างร่างขายต่อจากรายการซื้อเข้าได้
- Dashboard สำหรับโรงงานทั้งสองประเภท พร้อม AI ช่วยกรอก
- Matching ทั้ง 4 เส้นทาง พร้อมเหตุผลและข้อมูลที่ยังขาด
- ส่งข้อเสนอและยืนยันข้อตกลง พร้อมควบคุมปริมาณและแจ้งเตือน
- การประเมินภาพเบื้องต้นแบบไม่ขวางขั้นตอนหลัก
- การตรวจสิทธิ์ การกันงานซ้ำ และการรับมือ AI/ข้อความแจ้งเตือนล้มเหลว

### ทำเมื่อส่วนหลักผ่านแล้ว

แผนที่ Leaflet, การปรับแต่ง Flex Message เพิ่มเติม และตัวกรอง/สถิติขั้นสูง สิ่งเหล่านี้ไม่แทนที่ฟีเจอร์หลักที่ระบุข้างต้น

### หลัง MVP

ระบบชำระเงิน/escrow, ติดตามขนส่งและงานอัด, เอกสารการค้าเต็มรูปแบบ, เกรดคุณภาพรับรอง, เทรนโมเดล, ราคาตลาดสด, คาร์บอนเครดิต, แอปมือถือแยก, ระบบหลายผู้ดูแลต่อองค์กรขั้นสูง และระบบคงคลังการผลิตเต็มรูปแบบ

## 18. ข้อมูลเดโมและแนวทางตรวจสอบ

เตรียมเกษตรกรอย่างน้อย 2 ราย โรงงานอัด 1 แห่ง โรงงานปลายทาง 2 แห่ง พร้อมวัสดุ/ความต้องการที่มีทั้งคู่ตรงเงื่อนไขและไม่ตรงเงื่อนไข ข้อมูลสมมติต้องติดป้ายเดโมและแยกจากข้อมูลจริง

ทดสอบ 3 เรื่องราวหลัก: ขายตรง / จ้างอัด / ซื้อเข้าแล้วขายต่อ พร้อมกรณีปฏิเสธข้อเสนอ ราคาไม่ตรง ไม่มีพิกัด ปริมาณบางส่วน และร่างที่แก้หลังส่งปุ่มยืนยัน

ทดสอบอัตโนมัติที่กติกาสำคัญ: การจับคู่และหน่วย, สิทธิ์ข้ามองค์กร, transaction ปริมาณ, การรับข้อเสนอซ้ำ, การจัดสรรขายต่อ, การตรวจ webhook และผล AI ที่ไม่ผ่าน schema ส่วนหน้าจอและบทสนทนาตรวจครบเส้นทางด้วยบัญชีทดสอบจริง

## 19. การตั้งค่าและการส่งมอบ

เตรียม environment แยก development/demo โดยมี `DATABASE_URL`, ค่า session/auth, ค่าบริการเว็บ/API, AWS Region, Bedrock text/vision model ID, S3 bucket และ LINE channel secret/access token แยก 3 บัญชี เก็บค่าลับฝั่ง server เท่านั้น ไฟล์ตัวอย่างต้องไม่มีค่าลับจริง

การเข้าถึง AWS ใช้ role/temporary credentials ตามที่ hosting รองรับ จำกัดสิทธิ์ตามงานที่ใช้ ตรวจ configuration จริงก่อน deploy และไม่ฝังคีย์ในโค้ดหรือส่งให้ frontend

รูปและข้อมูลติดต่อไม่เปิดสาธารณะโดยอัตโนมัติ ตรวจสิทธิ์ก่อนให้ URL ภาพ จำกัดชนิด/ขนาดไฟล์และอายุ URL เก็บ log เท่าที่จำเป็น โดยหลีกเลี่ยงข้อความส่วนตัวและค่าลับ

สิ่งที่ต้องส่งท้าย MVP:

1. โค้ดพร้อม migrations และข้อมูลเดโมที่รันซ้ำได้
2. วิธีตั้งค่า 3 OA, Bedrock, ฐานข้อมูล และพื้นที่เก็บภาพ
3. ลิงก์ Dashboard และ QR/ลิงก์เพิ่มเพื่อนแต่ละบทบาท
4. คู่มือเดโม 3 เรื่องราวหลักและผล acceptance checks
5. รายการข้อจำกัด งานหลัง MVP และค่า configuration ที่ยังต้องกำหนดจากบัญชีจริง

เอกสารนี้กำหนดเป้าหมายสำหรับพัฒนาต่อ ไม่ใช่รายงานว่ามีการสร้าง ทดสอบ หรือ deploy ระบบจริงแล้ว
